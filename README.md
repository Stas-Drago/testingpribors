# Генератор черновиков карточек товаров

Локальный прототип для подготовки B2B-карточки контрольно-измерительного прибора. Принимает
JSON с исходными данными, создаёт текстовые поля карточки через Ollama и возвращает JSON и
Markdown. Это черновик: перед публикацией контент-менеджер проверяет свободный текст и
предупреждения.

## Возможности

- SEO-заголовок (до 70 символов), описание (800–1 200 символов), 3–5 поисковых запросов и
  коммерческий блок.
- Характеристики и перечень пропусков формируются приложением из входа, а не моделью.
- Числа в сгенерированном тексте сверяются с числовыми токенами входных данных; неподтверждённые
  числа дают предупреждение для ручной проверки, но это не доказывает фактическую ошибку.
- При нарушении структуры/ограничений текста допускается одна попытка исправления.
- Веб-интерфейс с JSON-редактором, предпросмотром, вкладками Markdown/JSON и отдельным копированием.
- Единственный LLM-провайдер — локальный Ollama; внешние LLM API и ключи не используются.

## Требования и установка

Нужны Python 3.11+, Docker для тестов и установленная Ollama с моделью. По умолчанию
используется `qwen3:8b`; другой локальный tag можно задать в `.env`.

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -e ".[dev]"
cp .env.example .env
ollama list
```

Убедитесь, что Ollama работает и выбранная модель уже загружена. При необходимости измените
`OLLAMA_MODEL`, `OLLAMA_BASE_URL` или `LLM_TIMEOUT_SECONDS` в `.env`. `.env` игнорируется Git;
секреты/ключи не требуются. Импорт приложения и `/health` работают и без доступной модели, но
генерация в этом случае вернёт безопасную ошибку.

## Запуск

```bash
uvicorn app.main:app --reload
```

- Веб-панель: <http://127.0.0.1:8000>
- Swagger/OpenAPI: <http://127.0.0.1:8000/docs>
- Проверка приложения: `GET /health` → `{"status":"ok"}` (без вызова Ollama)
- Генерация: `POST /api/products/draft`

Пример запроса:

```json
{
  "name": "Манометр показывающий DM 02",
  "manufacturer": "Манотомь",
  "specs": {
    "диапазон измерений": "0–1,6 МПа",
    "класс точности": "1,5",
    "присоединение": "G1/2",
    "диаметр корпуса": "100 мм"
  },
  "description": "Прибор предназначен для измерения избыточного давления."
}
```

Пример вызова:

```bash
curl -X POST http://127.0.0.1:8000/api/products/draft \
  -H 'Content-Type: application/json' \
  --data-binary @examples/product_1.json
```

Форма ответа (значения ниже обозначают форму контракта; фактические поля содержат результат
генерации):

```json
{
  "draft": {
    "seo_title": "…",
    "seo_description": "…",
    "characteristics": [{"name": "диапазон измерений", "value": "0–1,6 МПа", "source": "specs"}],
    "search_queries": ["…", "…", "…"],
    "commercial_block": "…",
    "missing_data": [],
    "warnings": []
  },
  "markdown": "# Черновик карточки товара\\n…"
}
```

Коды ошибок: `422` — JSON/схема входа; `503` — модель не задана или Ollama недоступна;
`502` — ошибка провайдера или некорректный ответ после исправления; `504` — тайм-аут.
Ответы ошибок не раскрывают тело ответа Ollama или внутренние исключения.

## Промпт и защита от выдуманных характеристик

Системные инструкции в `app/services/prompt_builder.py` задают русский язык, формат и
запрет на неподтверждённые технические сведения. JSON товара передаётся отдельным явно
недоверенным блоком; текст из полей товара не трактуется как инструкции. Модель генерирует
только заголовок, SEO-описание, поисковые запросы и коммерческий блок. Приложение независимо
копирует характеристики из `specs`, подставляет «данных нет» для пустых значений и вычисляет
отсутствующие разделы. Ollama получает JSON Schema, а Pydantic и прикладной валидатор повторно
проверяют ответ.

## Примеры

- [`examples/product_1.json`](examples/product_1.json) — манометр DM 02 из условия.
- [`examples/product_2.json`](examples/product_2.json) — Fluke 117; подтверждённые поля и
  официальный источник перечислены в [`examples/SOURCES.md`](examples/SOURCES.md).
- [`examples/generated_results.md`](examples/generated_results.md) — два фактических ответа
  `qwen3:8b` с длинами полей. Это результаты модели, не ручные образцы; перед публикацией
  проверяйте формулировки по источнику товара.

Чтобы повторить живую генерацию обоих примеров, из корня проекта с запущенной Ollama выполните:

```bash
python -m scripts.generate_examples
```

Скрипт пишет файл только после успешной генерации и валидации обоих товаров. Если приложение
запущено внутри Docker на macOS, укажите адрес хоста и увеличенный тайм-аут:

```bash
docker compose -p product-card-generator run --rm \
  -e OLLAMA_MODEL=qwen3:8b \
  -e OLLAMA_BASE_URL=http://host.docker.internal:11434 \
  -e LLM_TIMEOUT_SECONDS=240 \
  tests python -m scripts.generate_examples
```

## Тесты и проверки

В соответствии с `Ruls.md` запускайте проверки в Docker:

```bash
docker compose -p product-card-generator run --rm tests python -m pytest
docker compose -p product-card-generator run --rm tests python -m ruff check app tests
```

Unit- и API-тесты используют mock-клиенты и не требуют запущенной Ollama.

## Ограничения

- Проверка числовых токенов — эвристика, она не подтверждает семантическую истинность текста.
- Качественная генерация SEO-описания длиной 800–1 200 символов зависит от локальной модели;
  результат нужно проверить вручную.
- Поддерживается один товар за запрос; история, база данных, аутентификация, пакетная загрузка,
  CMS и публикация карточек отсутствуют.
- Автоматическая проверка чисел не доказывает семантическую достоверность; например, в
  фактическом ответе для DM 02 есть формулировки о стабильности показаний и монтаже, которых
  нет в исходном примере. Их нужно проверить или убрать перед публикацией.
