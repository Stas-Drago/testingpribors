# Архитектура, этапы реализации и журнал прогресса

## 1. Цель и границы MVP

Создать локальный прототип для контент-менеджера B2B-интернет-магазина. Сервис принимает
JSON одного контрольно-измерительного прибора через API или простую веб-форму, вызывает
локальную LLM через Ollama и возвращает проверяемый черновик карточки товара в JSON и Markdown.

Для каждого товара формируются:

- SEO-заголовок длиной не более 70 символов.
- SEO-описание длиной 800–1 200 символов.
- Структурированный список характеристик.
- От 3 до 5 поисковых запросов.
- Краткий коммерческий блок: кому подходит прибор и какие задачи решает.
- Перечень отсутствующих входных сведений и предупреждений.

Технические значения в списке характеристик копируются кодом из исходного JSON. Модель
не генерирует и не переписывает этот список. Свободный текст модели может содержать
неподтверждённые утверждения, поэтому он проверяется валидатором и контент-менеджером.
Сервис не публикует карточки автоматически.

В MVP входят Python API, простая форма, один товар на запрос, одна локальная модель через Ollama,
два примера товаров, тесты и инструкция локального запуска. База данных, авторизация,
CMS, массовая обработка и деплой не входят.

## 2. Технологический стек и конфигурация

- Python 3.11+.
- FastAPI — HTTP API, обработчики ошибок и OpenAPI-документация.
- Pydantic 2 и `pydantic-settings` — входные/выходные схемы и настройки.
- Ollama локально; вызовы локального API выполняются через `httpx`.
- Ollama Chat API (`/api/chat`) с JSON Schema в поле `format` для структурированного ответа.
- Используется уже скачанная пользователем модель; точный tag задаётся через `OLLAMA_MODEL`
  после проверки `ollama list`. Поддержку JSON Schema и качество русского текста нужно проверить
  для конкретной модели.
- Jinja2 и HTML + небольшой vanilla JavaScript — форма ввода и вывод/копирование результата.
- pytest и HTTPX — unit- и API-тесты; вызовы провайдера в автотестах заменяются mock-клиентом.
- Ruff — статическая проверка Python-кода.
- GitHub — хранение завершённого результата в ветке `codex/product-card-generator`.

Ollama должна быть установлена и запущена на локальной машине. Базовый URL API по умолчанию —
`http://localhost:11434`; облачный endpoint не используется. Перед интеграцией нужно проверить
доступность сервера и имя загруженной модели через `ollama list`.

Переменные окружения:

| Имя | Назначение | Пример безопасного значения |
|---|---|---|
| `OLLAMA_MODEL` | Tag локальной модели | `qwen3:8b` |
| `OLLAMA_BASE_URL` | Адрес локального Ollama API | `http://localhost:11434` |
| `LLM_TIMEOUT_SECONDS` | Тайм-аут одного запроса | `30` |

В `.gitignore` исключён `.env`; в репозитории хранится только `.env.example`. API-ключ не
требуется. Автотесты используют mock HTTP-транспорт; живые вызовы требуют запущенного Ollama
и указанного локального model tag.

## 4. Контракты и поток обработки

### Вход `ProductInput`

- `name: str` — обязательное непустое название.
- `manufacturer: str | null` — необязательный производитель.
- `specs: dict[str, str]` — произвольные пары «название характеристики → исходное значение».
- `description: str | null` — необязательное описание или фрагмент паспорта.

Пустые строки нормализуются в отсутствие значения. Лишние ключи и неверные типы
отклоняются с HTTP 422 и сообщением о поле. `specs` может быть пустым. Не вводить
универсальный список характеристик, обязательных для всех видов приборов.

### Выход `ProductDraft`

- `seo_title: str` — не более 70 символов.
- `seo_description: str` — 800–1 200 символов включительно, подсчёт Python `len()`.
- `characteristics: list[{name, value, source}]` — создаётся приложением из `specs`.
- `search_queries: list[str]` — от 3 до 5 элементов.
- `commercial_block: str` — назначение/польза, поддержанные входным описанием.
- `missing_data: list[str]` — только отсутствующие разделы входа и явно пустые поля.
- `warnings: list[str]` — замечания о длине или потенциально неподтверждённых утверждениях.

Если `specs` пуст — указать «Технические характеристики: данных нет». Если значение
характеристики пустое — оставить её название и показать «данных нет». Не объявлять
параметр отсутствующим, если вход не показывает, что он применим к этому прибору.

### Поток

```text
GET / или POST /api/products/draft
  → Pydantic проверяет JSON и нормализует вход
  → код готовит исходные факты, характеристики и список видимых пропусков
  → prompt_builder отделяет инструкции от JSON-данных товара
  → llm_client вызывает локальный Ollama API с JSON Schema для текстовых полей
  → validator проверяет длины, число запросов и потенциально новые числа
  → приложение добавляет характеристики из исходного JSON
  → renderer формирует Markdown; API возвращает JSON и Markdown
```

API:

- `GET /` — HTML-форма, принимающая JSON одного товара; показывает JSON/Markdown и кнопку копирования.
- `POST /api/products/draft` — один `ProductInput`, ответ `DraftResponse` с `draft` и `markdown`.
- `GET /health` — `{"status":"ok"}`, без вызова модели и без требования API-ключа.

Ошибки: 422 для неверного входа, 503 для недоступной локальной модели, 502 для
ошибки провайдера/невалидного результата после ограниченного повтора, 504 для тайм-аута.
В ответ не включать секрет, полный текст исключения или содержимое заголовков авторизации.

тестов и записи результата в журнал прогресса ниже. Тесты LLM используют mock HTTP-транспорт,
чтобы быть повторяемыми и не зависеть от локальной модели. Реальный вызов выполняется в
финальной ручной проверке при запущенном Ollama.

### Этап 3. Локальная модель Ollama и структурированный ответ

**Подэтапы:**

3.1. До реализации проверить `ollama list`, записать точный tag уже скачанной модели в
`.env` и проверить, что локальный сервер отвечает. В `.env.example` не указывать личные

3.2. Заменить настройки этапа 1: удалить зависимость приложения от `OPENROUTER_API_KEY`,
`OPENROUTER_MODEL` и OpenRouter URL; добавить `OLLAMA_MODEL` и `OLLAMA_BASE_URL`, сохранив
положительный `LLM_TIMEOUT_SECONDS`. Не требовать запущенный Ollama для импорта приложения,
`/health` и unit-тестов.

3.3. В `llm_client.py` использовать `httpx` для локального `POST /api/chat`: передавать
`model`, system/user messages, `stream: false` и JSON Schema в `format`. Не использовать
внешние API, OpenAI SDK или API-ключ; строить URL от `OLLAMA_BASE_URL`.

3.4. Схема ответа модели содержит только текстовые поля; `additionalProperties: false`,
все ключи обязательны. Не полагаться на JSON Schema для ограничения длины SEO-полей;
длину проверять прикладным валидатором.

3.5. Обработать недоступный сервер/модель, тайм-аут, HTTP-ошибки, отказ модели,
некорректный или неполный ответ. Не логировать полный текст товара или потенциально
чувствительные данные. Не повторять сетевой запрос при ошибке; повтор для исправления
SEO-длины будет ограничен одним разом на следующем этапе.

**Тесты этапа:** проверить URL/model/messages/schema mock HTTP-транспортом, разбор корректного
ответа, конфигурацию без модели, недоступность Ollama, тайм-аут, HTTP 4xx/5xx, отказ,
malformed response. Тесты не требуют установленного или запущенного Ollama:
`python -m pytest tests/test_llm_client.py tests/test_schemas.py`.

**Условие перехода:** приложение использует только локальный endpoint Ollama; при рабочем
локальном сервере и tag модели тестовый запрос возвращает нормализованный объект, а ошибки
преобразуются в безопасные доменные исключения. Результат живой проверки записать в журнал.

### Этап 4. Валидация текста и Markdown-рендеринг

**Подэтапы:**

4.1. В `validator.py` проверять заголовок ≤70 символов, описание 800–1 200 символов,
число запросов 3–5, непустые обязательные текстовые поля и типы.

4.2. Сравнивать числовые токены свободного текста с числами из входа. Неизвестное число
добавляет предупреждение для ручной проверки; автоматическая эвристика не объявляется
доказательством полноты/истинности семантического текста.

4.3. При ошибке формата или ограничений длины дать модели одну попытку исправить только
текстовые поля; повторно валидировать. После второй неудачи вернуть контролируемую ошибку.

4.4. В `renderer.py` отобразить все поля в читабельном русском Markdown с отдельными
разделами для характеристик, пробелов и предупреждений.

**Тесты этапа:** значения 69/70/71 для заголовка; описания ниже 800, ровно 800, ровно
1 200 и выше; 2/3/5/6 запросов; совпавшие и неподдержанные числа; пустые specs; экранирование
Markdown-спецсимволов; успешный retry, отсутствие retry при ошибке провайдера и контролируемая
ошибка после второй неудачи. Запуск тестов в Docker:
`docker compose -p product-card-generator run --rm tests python -m pytest tests/test_validator.py tests/test_renderer.py tests/test_draft_service.py tests/test_llm_client.py tests/test_prompt_builder.py`.

**Условие перехода:** корректный черновик соответствует ограничениям; недопустимый текст
исправляется не более одного раза либо завершается понятной ошибкой.

- Каждый этап имеет тестовые ворота; провал теста возвращает работу на исправление в текущем этапе.

  загруженной модели; без них этап интеграционных примеров остаётся незавершённым.

- Не отмечать шаг завершённым до прохождения его критериев.
- Коммит и push выполняются один раз после полного набора проверок, в feature-ветку.

## 8. Известные ограничения и последующие улучшения

Автоматическая проверка чисел и JSON Schema не доказывают истинность всего свободного
текста. Контент-менеджер проверяет SEO-описание и коммерческий блок перед публикацией.
Вне MVP остаются пакетная загрузка, история генераций, редактирование и сохранение
черновиков, несколько LLM-провайдеров и подтверждение фактов с точными ссылками на
фрагменты паспорта.
